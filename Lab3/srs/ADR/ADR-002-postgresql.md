# ADR-002: PostgreSQL как основная СУБД TrustRate

## Контекст и постановка задачи
Система хранит пользователей, сделки, отзывы, счета TC, транзакции, проверки и жалобы. Данные связаны внешними ключами, а операции с балансом требуют транзакционности. Какую СУБД использовать?

## Драйверы решения
- Транзакционная целостность.
- Внешние ключи и уникальные ограничения.
- Совместимость с Java и Spring Data JPA/Hibernate.
- Поддержка агрегирующих запросов для рейтинга.
- Инструменты миграции и резервного копирования.

## Рассмотренные варианты
- PostgreSQL.
- MySQL.
- MongoDB.

## Итог решения
Выбран **PostgreSQL**, поскольку модель TrustRate реляционная, а целостность связей между сделками, отзывами и транзакциями TC критична. Этот выбор соответствует технологическому стеку SRS.

### Последствия
- Хорошо: транзакции, внешние ключи, ограничения и индексы.
- Хорошо: интеграция с JPA/Hibernate.
- Плохо: необходимо управлять миграциями и резервными копиями.
- Плохо: БД требует отдельной настройки и сопровождения.

### Подтверждение
Интеграционные тесты проверяют уникальность отзывов, внешние ключи, атомарность баланса TC и откат транзакции при ошибке. Структура БД обновляется миграциями.

## Плюсы и минусы вариантов

### PostgreSQL
- Хорошо: строгая ссылочная целостность.
- Хорошо: транзакции и сложные запросы.
- Хорошо: соответствует SRS.
- Плохо: нужно сопровождать схему и резервное копирование.

### MySQL
- Хорошо: зрелая реляционная СУБД с транзакциями.
- Нейтрально: технически подходит.
- Плохо: переход с уже выбранной PostgreSQL не даёт очевидной выгоды и потребует изменения конфигурации.

### MongoDB
- Хорошо: гибкая структура документов.
- Плохо: связи предметной области и ограничения придётся дополнительно контролировать приложением.
- Плохо: реляционная модель TrustRate естественнее выражается в PostgreSQL.
