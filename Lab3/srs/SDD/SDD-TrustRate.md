# 1. Введение

## 1.1 Назначение документа
SDD описывает архитектуру TrustRate на основе SRS. Документ предназначен для разработчиков, архитектора, тестировщиков и сопровождающих специалистов. Он фиксирует компоненты системы, их ответственность, модель данных, взаимодействия и ключевые проектные решения.

## 1.2 Область применения
TrustRate — веб-приложение для формирования репутации пользователей на основе завершённых сделок и отзывов. Система включает профили, сделки, отзывы, рейтинг, внутренние баллы доверия Trust Credits (TC), верификацию, жалобы и модерацию. В текущую область входят веб-интерфейс, серверная часть и реляционная БД. Реальные платежи, вывод TC в деньги, мобильные приложения и интеграция с государственными реестрами не входят.

## 2.2 Выбранные точки зрения
Выбраны контекстная, композиционная, логическая, информационная, интерфейсная, интерактивная, алгоритмическая, динамическая, безопасностная и deployment-точки зрения.

### 2.2.1 Контекст
Акторы: гость, пользователь, модератор, администратор. Браузер взаимодействует с TrustRate по HTTPS. Для подтверждения email и телефона предусматриваются внешние почтовый и SMS-провайдеры. Платёжная система не требуется.

### 2.2.2 Композиция
Логические компоненты:
1. Web/UI — веб-страницы.
2. Authentication & Authorization — регистрация, вход, роли.
3. User Profile — профиль и уровень верификации.
4. Deal Management — сделки и переходы статусов.
5. Review Management — отзывы и правила публикации.
6. Rating Engine — расчёт рейтинга.
7. Trust Credits Ledger — баланс и история операций TC.
8. Verification — email, телефон и ручная проверка документов.
9. Antifraud — обнаружение подозрительной активности.
10. Moderation & Appeals — жалобы, решения и апелляции.
11. Audit & Notifications — аудит и уведомления.
12. Persistence — репозитории и PostgreSQL.

### 2.2.3 Логическое представление
Основные сущности: `User`, `UserProfile`, `Deal`, `Review`, `TrustAccount`, `TrustTransaction`, `VerificationRequest`, `Complaint`, `ModerationCase`, `Appeal`, `AuditEvent`. Один пользователь имеет один профиль и один счёт TC; сделка связывает двух участников; участник может оставить не более одного отзыва контрагенту в рамках сделки; пользователь может иметь несколько запросов верификации, жалоб и записей аудита.

### 2.2.4 Физическое представление
Предполагаемая схема: браузер → HTTPS → Spring Boot application → PostgreSQL. Внешние email/SMS-сервисы подключаются через адаптеры. Конкретный хостинг и production-инфраструктура исходными требованиями не определены.

### 2.2.5 Структура
Пакеты: `controller`, `service`, `domain`, `repository`, `security`, `dto`, `config`, `audit`. Контроллеры отвечают за HTTP и валидацию, сервисы — за бизнес-сценарии, репозитории — за доступ к данным. Контроллеры не должны напрямую обращаться к репозиториям.

### 2.2.6 Зависимости
Технологический стек SRS: Java 17, Spring Boot, Spring Security, Spring Data JPA/Hibernate, Maven, PostgreSQL, Thymeleaf. Внешние почтовый и SMS-провайдеры пока не выбраны.

### 2.2.7 Информация
Предлагаемые таблицы: `users`, `user_profiles`, `deals`, `reviews`, `trust_accounts`, `trust_transactions`, `verification_requests`, `complaints`, `moderation_cases`, `appeals`, `audit_events`. Необходимы внешние ключи и уникальные ограничения. Один автор не может создать два отзыва по одной сделке. Обновление баланса TC и создание записи транзакции выполняются атомарно.

### 2.2.8 Интерфейс
Русскоязычный адаптивный веб-интерфейс: регистрация/вход, профиль, сделки, отзывы, рейтинг, история TC, верификация, жалобы и уведомления. Модератору доступна очередь проверок, администратору — управление ролями и настройками.

### 2.2.9 Взаимодействие
Сценарий: пользователь инициирует завершение сделки → сервис проверяет участника и допустимость перехода → сделка получает статус `Completed` → участники отправляют отзывы → сервис проверяет право автора и отсутствие дубликата → отзывы ожидают совместной публикации согласно SRS → antifraud проверяет признаки риска → допустимые отзывы передаются Rating Engine → выполняется расчёт рейтинга → при наличии основания проводится транзакция TC → Audit фиксирует действие.

### 2.2.10 Алгоритм рейтинга
Формула из SRS:
`weight = author_trust_coefficient × recency_coefficient × deal_value_coefficient`
`rating = Σ(score × weight) / Σ(weight)`
Отзывы на antifraud-проверке исключаются. Коэффициенты, шкала оценки и точные правила нормализации требуют согласования. В исходном SRS предварительно указаны минимум 3 отзыва для показа рейтинга и окно актуальности 14 дней.

### 2.2.11 Динамика состояний
Статусы сделки: `Created`, `In progress`, `Completed`, `Cancelled`, `Under review`. Переходы централизованы в сервисе сделок. Запрос верификации проходит `Pending`, `Approved`, `Rejected`. Жалоба/апелляция проходит `Submitted`, `In review`, `Resolved`. Точный жизненный цикл отзыва следует сверить с SRS при реализации.

### 2.2.12 Параллелизм
Для защиты от двойного начисления TC и повторных отзывов применяются транзакции БД, уникальные ограничения и идемпотентность повторных запросов. Баланс и запись `TrustTransaction` изменяются в одной транзакции.

### 2.2.13 Паттерны
Используются Layered Architecture, Repository, Service Layer, DTO, Strategy для вариантов расчёта рейтинга и явная машина переходов статусов. Не следует вводить паттерны без практической необходимости.

### 2.2.14 Развёртывание
Сборка — Maven; приложение — Spring Boot; БД — отдельный PostgreSQL. Для разработки оба компонента могут работать локально. Production-хостинг и CI/CD не определены.

### 2.2.15 Ресурсы
Критические ресурсы: соединения PostgreSQL, CPU при пересчёте рейтинга, хранилище документов верификации, место под аудит. Размер и тип загружаемых файлов должны ограничиваться. Исходный SRS указывает максимальный срок хранения изображений документов 30 дней.

# 3. Проектные представления

### DV-001 — Контекст системы
**Viewpoint:** Context.  
**Representation:** браузер пользователей → TrustRate; внешние интеграции — email и SMS. Акторы: гость, пользователь, модератор, администратор.  
**More Information:** SRS, внешние интерфейсы и безопасность.

### DV-002 — Компонентная архитектура
**Viewpoint:** Composition / Structure.  
**Representation:** Web/UI → Controller → Service Layer → Domain/Repository → PostgreSQL. Сервисы разделены по профилям, сделкам, отзывам, рейтингу, TC, верификации, antifraud и модерации.  
**More Information:** ADR-001.

### DV-003 — Модель данных
**Viewpoint:** Information / Logical.  
**Representation:** User 1:1 UserProfile; User 1:1 TrustAccount; Deal связывает двух User; Deal 1:N Review; User 1:N TrustTransaction; User 1:N VerificationRequest.  
**More Information:** ADR-002, ADR-003.

### DV-004 — Сценарий сделки и отзывов
**Viewpoint:** Interaction.  
**Representation:** проверка участника → завершение сделки → отправка отзывов → публикация по правилам SRS → antifraud → рейтинг → TC → аудит.  
**More Information:** требования SRS по сделкам, отзывам, рейтингу и TC.

### DV-005 — Состояния сделки
**Viewpoint:** State Dynamics.  
**Representation:** `Created → In progress → Completed`; альтернативные исходы — `Cancelled` или `Under review` при условиях, определённых бизнес-правилами.  
**More Information:** Deal Management.

### DV-006 — Развёртывание
**Viewpoint:** Deployment.  
**Representation:** Browser —HTTPS→ Spring Boot —JDBC→ PostgreSQL; внешние email/SMS сервисы подключаются через интеграционные адаптеры.  
**More Information:** конкретная инфраструктура требует отдельного решения.

### DV-007 — Ролевая модель
**Viewpoint:** Security.  
**Representation:** Guest — публичный доступ; User — собственный профиль, сделки и отзывы; Moderator — жалобы и проверки; Admin — роли и настройки. Проверка прав выполняется на сервере.  
**More Information:** Spring Security и требования безопасности SRS.

# 5. Приложения: вопросы для согласования

1. Утвердить базовую ставку начисления TC и стартовый баланс.
2. Утвердить шкалу оценки и коэффициенты рейтинга.
3. Уточнить сроки и правила публикации отзывов, если второй участник не оставил отзыв.
4. Выбрать email- и SMS-провайдеров.
5. Определить production-инфраструктуру, резервное копирование и восстановление.
6. Согласовать сроки хранения документов и журналов аудита.

TC не являются деньгами. Antifraud-сигнал сам по себе не является доказательством нарушения. Автоматическое наказание без решения модератора не допускается.
